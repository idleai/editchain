# EC03 storage and operation IDs

New chains use EC03 frames and 256-bit canonical operation IDs. EC02 chains remain
readable. Migrate them to a new directory before appending with the new writer:

```sh
editchain --chain /path/to/old-chain migrate --destination /path/to/new-chain
editchain --chain /path/to/new-chain --output json integrity
```

## IDs and queries

`OpId` is 32 bytes. JSON and machine output use all 64 lowercase hexadecimal
digits. Human CLI query output uses the shortest unique prefix of at least 12 digits.
ID arguments and `--after` accept unambiguous prefixes of 4–64 digits; ambiguous
prefixes fail, including when one candidate is quarantined. Structured JSON
references require complete IDs. Prefixes are local queries and must not be saved
as durable references; a later import can make a formerly unique prefix ambiguous.

Producer identity is separate: `SourceId { node: u64, boot: u32, seq: u64 }`.
For older producers and wire-only migration, derive the canonical ID using BLAKE3
in derive-key mode, with context `editchain.operation-id.v1` and exactly these
20 bytes: `node.to_le_bytes() || boot.to_le_bytes() || seq.to_le_bytes()`.
For example, `1:0:42` maps to:

```text
14721180b5564d64c8b55873b00e440aa49105bd3d1350fa3412e285beba758c
```

In the older envelope, `Op.source` retains that source identity. When supplied,
it must derive to `Op.id`.
Callers may supply a complete opaque ID with no source. This is an identity hash,
not a content hash: different bytes under one ID still cause quarantine. Hash
order carries no producer order, time, or causal meaning. Causal parents and
explicit source identity supply those facts.

Legacy colon addresses and JSON tuple objects remain accepted at input boundaries
and translate deterministically. Typed parents, note targets and Git operation
references migrate by the same rule, including references whose targets are absent.
Opaque provider and human metadata keeps its original bytes and versioned source
addresses. Physical operation-schema conversion assigns new observation IDs and
stores old-address mappings inside converted records; its alias index is rebuildable.
Schema-three records also have a separate logical `item` ID. See
[operations.md](operations.md) for this envelope and its migration contract.

## Frame contract

All integers below are little-endian. The current EC03 **wire version is 2**;
version 1 was an unused prototype and is rejected. Framing and operation schemas
have independent versions.

| Header offset | Size | Field |
| --- | --- | --- |
| 0 | 4 | Magic `EC03` |
| 4 | 2 | Wire version `2` |
| 6 | 2 | Header length `32` |
| 8 | 4 | Complete frame length, including final checksum |
| 12 | 4 | Record count |
| 16 | 8 | Page sequence; this implementation accepts values up to `u32::MAX` |
| 24 | 4 | Mandatory feature flags, currently zero |
| 28 | 4 | CRC32C of the preceding 28 bytes |

Each record is `length: u32`, `flags: u8`, `length` payload bytes, then a CRC32C
of those payload bytes. Flags are preserved as opaque recorded flags. A final CRC32C
covers the header and all records. CRC32C uses the Castagnoli/iSCSI parameters.
The header checksum, declared bounds, record count, every record checksum, and
final checksum must pass before any record in a frame becomes visible.

Records are limited to 64 MiB and frames to 128 MiB. Writers target roughly
1 MiB frames and roll segments at **32 MiB**; an individual larger record can
exceed the segment target. The inline payload cutoff remains **16 MiB** and the
source capture budget remains **512 MiB per file**. These are separate limits.

Interrupted trailing frames are reported and left intact; subsequent appends use
a new segment. A complete frame with a bad checksum or unsupported mandatory
features is an error, not an appendable tail. Indexed point reads also verify the
record checksum retained in their location.

## Operation schemas

Versioned records start with ten `ff` bytes, ASCII `ECR3`, and one schema byte.
This prefix cannot begin a valid legacy postcard operation ID.

- Schema 3: postcard encoding of the direct ten-type activity envelope described in
  [operations.md](operations.md). Canonical IDs stay 32 bytes. Application schema
  conversion belongs to producers; storage migration preserves the encoded records.
- Schema 1: postcard encoding of `id`, optional `source`, `parents`, `actor`,
  `clock`, `scope`, `tags`, and `kind`, in that order. Canonical IDs occupy 32
  fixed bytes. Existing operation-kind discriminants retain their order.
- Schema 2: exact legacy postcard bytes that decode successfully but differ from
  the legacy encoder's canonical spelling. Migration uses this preserved encoding to
  retain distinct byte variants and their quarantine behavior.
- Unversioned records: the frozen EC02 envelope. Readers translate its typed IDs.
  Unknown schemas remain retained bytes and are counted as undecodable.

Decoders reject trailing bytes and inconsistent source/ID pairs. Golden frame,
operation, and ID fixtures live in `editchain-store/src/format/tests/fixtures`
and the core golden tests. Schema changes require a new explicit version.

## Migration and recovery

Migration holds the source writer lock, converts into `DESTINATION.migrating`,
and checkpoints each completed source segment. The original segments are copied
byte for byte into `migration-v1/original/`; blobs and import cursors are copied
and verified. Complete unknown records and flags survive unchanged. Incomplete
source tails remain in the original archive and are reported.

Before publication, an independent conversion of the source must match the
ordered digest of exact destination record bytes, flags and lengths. The
`migration-v1/manifest.json` report records original segment hashes, counts,
phase timings, and the semantic digest. Only then is the staging directory
renamed into place. The source chain is retained.

Rerun the same command after interruption. Resume verifies completed original
segments, discards an uncheckpointed destination suffix, and continues. Ordinary
writers refuse a staging directory. Existing unrelated destinations are refused.
Allow space for the new chain plus its original-segment archive and rebuilt indexes.

Wire-only migration translates sharing exclusions, local record entries, and received-record receipts
to the new exact record hashes. An old segment cutoff becomes explicit exclusions
because segment boundaries change; migration does not grant additional sharing
consent. The policy revision advances. Damaged or incomplete policies fail migration.

The derived index rebuilds under `index-v3`. Old caches are left in the original
chain. Snapshot schema and peer protocol are version 5;
upgrade both replication peers together. Reconnect consumers and use full IDs or
newly resolved prefixes after switching to the migrated directory.
