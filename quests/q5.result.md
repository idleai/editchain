## Summary

Built a **text-only debugging harness** so the coding agent (deepseek-v4-flash, image-blind) can inspect, measure, interact with, and debug the rendered EditChain VS Code webview **without a human reloading the extension and visually checking it**. Every render is translated into textual/numeric evidence — no screenshots.

Two complementary harnesses, per the deep-research brief:

1. **Puppeteer standalone harness** — loads the exact production webview assets (`media/main.js` + `media/main.css`) into Chromium, reproduces states with deterministic fixtures or the real Rust service, and dumps full DOM/layout/SVG geometry as text.
2. **WebdriverIO real-VS-Code harness** — launches real VS Code (Extension Development Host) under Xvfb, opens the webview, injects the same probe, runs the identical textual checks, and scrolls through the full history.

The harness immediately surfaced **genuine layout findings** (dot-row misalignment, header overflow) that reproduce across both harnesses.

## Architecture

### Harness files (all under `extensions/vscode-editchain/`)

```
media/main.css                 — webview stylesheet extracted from extension.ts (shared by both hosts)
test/harness/index.html        — mounts main.css + main.js with a vscode shim; ?bridge=fixture|service
test/harness/fixtures.js       — deterministic protocol fixtures (7 scenarios)
test/harness/fixtureBridge.js  — vscode shim dispatching requests against fixtures
test/harness/serviceBridge.js  — vscode shim forwarding requests to the real Rust service
test/harness/layoutProbe.js    — window.__editchainDebug: whenIdle/dumpLayout/assertLayout/getMetrics
scripts/ui-dump.mjs            — ui:dump / ui:inspect / ui:check CLI commands
scripts/ui-real.mjs            — ui:real: render real .editchain data via the Rust service
scripts/ui-vscode-record.sh    — record the wdio session as MP4 (Xvfb + ffmpeg x11grab)
test/vscode/wdio.conf.ts       — WebdriverIO config (browserName: vscode, extensionPath, service binary)
test/vscode/history.e2e.ts     — real-VS-Code e2e: open webview, inject probe, scroll full history
test/vscode/tsconfig.json      — wdio types
```


## Key design decisions

- **Minimal-change bridge seam**: rather than rewriting `main.js`, the harness defines a global `vscode` shim (`postMessage`/`getState`/`setState`) before loading it. The renderer captures `acquireVsCodeApi()` at load time, so the bridge must be in place *before* `main.js` runs — solved via `?bridge=` selection in `index.html`.
- **CSS extraction**: moved the embedded `<style>` from `extension.ts::getHtml()` into `media/main.css` (verified byte-identical), so VS Code and Chromium share identical styles.
- **Protocol fixtures, not copied DOM**: fixtures model `editchain-protocol` response shapes (`HistoryRow`, `GraphLayout`, etc.), sliced by offset/limit like the real service.
- **Deterministic readiness**: `whenIdle()` resolves only when no request is in flight, fonts are loaded, and 2 animation frames are stable — no arbitrary sleeps.
- **Textual checks instead of pixel diffs**: every failure names a selector/key plus expected/actual/delta/tolerance.
- **Puppeteer over Playwright**: Chromium was already cached (`~/.cache/puppeteer`), so Puppeteer-core had zero browser download cost.
- **WebdriverIO for real VS Code**: `wdio-vscode-service` launches VS Code; requires `xvfb` on headless servers (VS Code's GUI binary needs a display).

## Text-only inspection contract

The probe (`window.__editchainDebug`) exposes:

- `whenIdle()` → resolves when the UI is settled (no in-flight request, fonts loaded, 2 stable rAFs).
- `dumpLayout()` → viewport, state, layout boxes, SVG dots/edges with geometry.
- `assertLayout()` → textual checks: header present, no horizontal overflow, dot-row alignment, column alignment.
- `getMetrics()` → render generation, DOM node count, listener count.

Artifacts written per run: `summary.md`, `layout.txt`, `layout.json`, `svg.json`, `console.txt`, `metrics.json`, `aria.yml` (fixture/real modes); plus `dom.json`/`dom.txt` (full DOM tree + computed styles) in real-data mode.

## Real VS Code harness

`test/vscode/history.e2e.ts` runs three tests:

1. Loads VS Code and asserts the workbench title contains `editchain`.
2. Opens the history explorer webview via `workbench.getWebviewByTitle('EditChain History')`, switches into its iframe, injects the same probe, and runs textual checks.
3. Scrolls through the full history (953 rows with submodules hidden) and verifies all rows render down to the genesis ChainStart op (`0:0:0`).

The scroll is **animated** (`smoothScrollTo` eases `scrollTop` over ~1.5s per pass) so rows visibly flow past in a recorded video.

## Findings surfaced by the harness

The harness immediately caught genuine layout issues that reproduce across both Puppeteer and WebdriverIO:

- **DOT_ROW_ALIGNMENT** — graph dots sit below row centers. The renderer mixes a hardcoded `ROW_H=34` with measured row heights; rows render ~22px tall. deltaY=6 in the harness, deltaY=8 in real VS Code.
- **NO_HORIZONTAL_OVERFLOW** — `.th.commit` header cell overflows past the viewport at wide widths (delta 9px in fixtures; 114px on real data at 1440px).
- **Racy oldest-op ordering** — under progressive loading, the relative order of the genesis ChainStart (`0:0:0`) and seed session's first op (`...:65536`) occasionally flips; the service's canonical order is stable.

These are surfaced as FAIL checks for the agent to fix, not test blockers.
