# Text-only debugging harness for the EditChain VS Code extension

**author:** GPT5.6 Sol (max)
**Prepared for:** ambientlight  
**Research date:** 2026-08-09  
**Repository:** [ambientlight/editchain](https://github.com/ambientlight/editchain)  
**Inspected revision:** [0c4ad672f055bb6f56f7133df05b75334f876f85](https://github.com/ambientlight/editchain/tree/0c4ad672f055bb6f56f7133df05b75334f876f85)

## Goal

Add a harness that lets a **text-only coding agent** inspect, measure, interact with, and debug the rendered EditChain VS Code extension without a person repeatedly reopening the extension and visually checking it.

The central constraint is absolute: **the agent cannot consume screenshots or any other image input**. Therefore, screenshots, pixel diffs, and image-based visual regression are outside the recommended agent workflow. The browser must translate the rendered UI into textual and numeric evidence.

This brief intentionally does not propose product fixes or audit the current UI. It only defines the additional debugging scaffolding.

## Recommended architecture

Use two complementary execution modes:

| Mode | Tool | Purpose |
|---|---|---|
| Fast render harness | Playwright Test + Chromium | Load the exact webview assets, reproduce states with fixtures, inspect complete textual layout, and run most debugging checks |
| Real VS Code harness | WebdriverIO + wdio-vscode-service | Launch the actual extension in VS Code, enter its webview, and verify that the same textual probe works in the real host |
| Optional interactive layer | Chrome DevTools MCP | Let the coding agent navigate the standalone harness, request textual snapshots, execute the probe, and inspect console/performance data |

The standalone Playwright harness should be the agent’s normal edit-run-debug loop. The real VS Code harness should validate integration after the faster harness passes.

## 1. Standalone Playwright render harness

Create a small HTML host that mounts the **same production webview renderer and stylesheet** used by the extension. It should not reimplement the UI.

The harness supplies a test version of acquireVsCodeApi with:

- postMessage;
- getState and setState;
- deterministic responses from fixtures;
- optional connection to the real Rust stdio service;
- controllable request delay and ordering.

This makes it possible to reproduce empty, loaded, filtered, searched, scrolled, resized, error, and large-history states without launching VS Code.

A minimal seam is enough:

~~~ts
interface HostBridge {
  postMessage(message: unknown): void;
  getState<T>(): T | undefined;
  setState(state: unknown): void;
}

function mountHistory(root: HTMLElement, bridge: HostBridge): HistoryView;
~~~

Production wraps acquireVsCodeApi. The harness supplies FixtureBridge or ServiceBridge.

Because the current webview CSS is embedded in extension.ts, the cleanest harness-enabling change is to move it to media/main.css and load that file from both hosts. This is scaffolding, not a visual redesign. The production extension and harness must use the same JavaScript, CSS, HTML structure, and theme variables.

Playwright is preferred over Puppeteer because it includes the runner, fixtures, locators, automatic waiting, traces, and snapshot assertions while still exposing the Chrome DevTools Protocol.

## 2. Real VS Code harness

Use [WebdriverIO with wdio-vscode-service](https://webdriver.io/docs/extension-testing/vscode-extensions/) for a smaller suite that:

1. launches a pinned VS Code build with the EditChain extension;
2. opens the fixture workspace;
3. invokes EditChain: Open History Explorer;
4. switches into the webview;
5. waits for the textual debug probe to become idle;
6. retrieves the same layout report used by Playwright;
7. interacts with search, filters, scrolling, row selection, and resize;
8. captures extension-host logs, webview console output, and probe results as text.

This validates the actual workbench, extension activation, native service, message bridge, iframe/webview environment, and panel lifecycle. It should not be the main iteration loop because launching VS Code is much slower than opening the standalone page.

The probe itself should be host-independent. Playwright and WebdriverIO should call the same JavaScript function and receive the same JSON schema.

## Text-only inspection contract

No screenshot should be required or generated for the agent. Each render should be translated into the following evidence.

### Semantic tree

Use Playwright’s [AI-mode ARIA snapshot](https://playwright.dev/docs/aria-snapshots) to report:

- roles and accessible names;
- input values and checked states;
- focus;
- disabled/expanded/selected state;
- bounding boxes when available;
- iframe contents.

This is concise and useful for interaction, but it is not a complete layout representation because generic divs and decorative SVG elements may be absent.

### Complete DOM and browser layout

Use [CDP DOMSnapshot.captureSnapshot](https://chromedevtools.github.io/devtools-protocol/tot/DOMSnapshot/) in the standalone harness. Normalize its interned arrays into a readable tree containing:

- tag, id, classes, stable data key, and abbreviated text;
- x, y, width, and height;
- visibility and intersection state;
- client, scroll, and offset dimensions;
- parent/child hierarchy;
- paint order;
- selected computed styles.

Request only useful styles:

~~~text
display, position, visibility, opacity, z-index,
overflow-x, overflow-y, grid-template-columns,
width, height, min-width, min-height,
padding, margin, font-size, line-height, white-space,
text-overflow, color, background-color,
border-color, pointer-events, transform
~~~

For the real VS Code run, the custom in-page probe can collect the same practical fields with DOM APIs even when raw CDP DOMSnapshot is inconvenient inside the nested webview.

### EditChain geometry

Add a small test-only probe using:

- getBoundingClientRect and getClientRects for rows and cells;
- scrollWidth/clientWidth and scrollHeight/clientHeight for overflow and truncation;
- getBBox and getCTM for SVG nodes and paths;
- getTotalLength and getPointAtLength for edge endpoints;
- document.elementFromPoint for occlusion and hit testing;
- IntersectionObserver calculations for visible/clipped regions;
- getComputedStyle for grid tracks, fonts, colors, and stacking.

The probe should link rendered objects using stable keys such as data-node-key and data-edge-key. It should describe relationships, not merely dump coordinates.

Example output:

~~~text
VIEWPORT 1440x900 dpr=1 theme=dark
STATE scenario=merge-filtered status=idle generation=12

#layout box=(0,61,1440,839)
  #rows box=(0,61,1440,839) scroll=(1440,1700) overflowY=auto
  header box=(0,61,1440,31) columns=[72,1012,140,108,108]
  row key=git:fe15 box=(0,92,1440,34)
    content box=(72,92,1012,34) truncated=false
    dot lane=2 center=(54,109) rowCenterDelta=(0,0)
  edge git:fe15->git:9a02 start=(54,109) end=(36,143)

CHECKS pass=24 fail=1
FAIL COLUMN_ALIGNMENT key=git:fe15 column=author
expectedLeft=1224 actualLeft=1226 delta=2 tolerance=0.75
~~~

This is the primary equivalent of “seeing” the UI for the text-only model.

### Textual checks instead of pixel checks

The harness should express visual problems as assertions:

- element boxes align within a tolerance;
- no unexpected horizontal or vertical overflow;
- a child is clipped by a named ancestor;
- an element is occluded according to hit testing;
- grid columns have matching boundaries;
- an SVG dot matches its row center;
- an SVG edge reaches its keyed nodes;
- a sticky element remains at the expected scrollport position;
- text is truncated or wrapped as expected;
- focus reaches interactive controls in order;
- computed colors meet numeric contrast requirements;
- rendered DOM size stays within a configured bound.

These checks are more useful to a text-only model than a pixel difference because every failure includes the object, expected value, actual value, delta, and likely cause.

The harness cannot replace human judgment about subjective polish, illustration quality, or subtle anti-aliasing. It can make layout, geometry, state, clipping, interaction, semantics, and performance directly debuggable without images.

## Deterministic readiness

Do not make the agent guess how long the UI needs to settle. Expose a test-only API:

~~~ts
window.__editchainDebug = {
  whenIdle(): Promise<RenderGeneration>,
  dumpLayout(scope?): LayoutDump,
  assertLayout(scope?): AssertionResult,
  getMetrics(): RenderMetrics
};
~~~

whenIdle should resolve only when:

- no request for the current generation is in flight;
- no render is queued;
- document.fonts.ready has completed;
- relevant MutationObserver and ResizeObserver activity has stopped;
- tracked rectangles are unchanged for two animation frames.

In harness mode, timers and progressive loading should be explicitly advanced or disabled. The agent should wait on state, never sleep for an arbitrary number of milliseconds.

The debug API should exist only in test/harness builds.

## Agent-facing commands and artifacts

Recommended commands:

~~~bash
npm run ui:dump -- --scenario merge-filtered --viewport 1440x900 --theme dark
npm run ui:inspect -- --scenario merge-filtered --selector "[data-node-key=git:fe15]"
npm run ui:check
npm run ui:vscode:dump
npm run ui:vscode:check
~~~

Each command should print a concise result and save deeper text files:

| Artifact | Content |
|---|---|
| summary.md | Scenario, state, counts, console errors, and failed checks |
| aria.yml | Textual accessibility tree |
| layout.txt | Human-readable DOM/layout hierarchy |
| layout.json | Full normalized machine representation |
| svg.json | Dots, lanes, paths, endpoints, boxes, and transforms |
| console.txt | Browser/webview console output |
| metrics.json | Render timing, DOM/listener counts, layout/style counters |
| domsnapshot.json | Raw CDP snapshot for targeted queries |

Do not print the raw DOM snapshot into the agent context. Save it and tell the agent which selector, node key, or JSON path to query. Truncate long text in layout.txt while retaining full text length and a content hash in JSON.

No PNG, JPEG, screenshot, or pixel-diff artifact is part of the required workflow.

## Fixtures

Keep fixtures small and diagnostic:

- empty, loading, success, and service error;
- linear graph, fork, merge, crossing lanes, and offscreen edges;
- multiple sessions and repositories;
- messages, tools, system rows, and submodules;
- search and filter states;
- long, Unicode, emoji, and RTL text;
- narrow, medium, and wide viewports;
- light, dark, and high-contrast theme tokens;
- short and delayed/reordered service responses;
- virtual large-history windows.

Fixtures should model protocol responses, not copied DOM. A service-backed mode should also start editchain-vscode-service and exercise the real framed stdio protocol.

## Optional Chrome DevTools MCP

The official [Chrome DevTools MCP server](https://github.com/ChromeDevTools/chrome-devtools-mcp) is useful if the coding agent can call MCP tools. Point it at the standalone harness and use it to:

- open a scenario;
- retrieve a text accessibility snapshot;
- execute window.__editchainDebug.dumpLayout;
- inspect console and network messages;
- start a performance trace and return numeric/text summaries.

It should be an interactive convenience, not a dependency of CI. Use a disposable Chrome profile because browser-debugging access can expose page contents.

## Implementation sequence

1. Extract/share the webview stylesheet and create the HostBridge seam.
2. Add FixtureBridge, a handful of deterministic scenarios, and whenIdle.
3. Implement the DOM/layout/SVG probe and text formatter.
4. Add ui:dump, ui:inspect, and ui:check.
5. Add service-backed harness mode.
6. Add the small WebdriverIO real-VS-Code suite.
7. Optionally document the Chrome DevTools MCP workflow.

A first useful version only needs steps 1–4. It will already let the text-only agent reproduce a UI state, inspect exact rendered geometry, identify a failing element, and rerun after a code change without manually reopening VS Code.

## Definition of done

The harness is successful when:

- the agent runs one command after a UI edit;
- the exact production webview assets render in Chromium;
- the output contains no image dependency;
- every failure names a selector or stable node key plus expected, actual, delta, and tolerance;
- the agent can query DOM hierarchy, computed styles, boxes, overflow, clipping, hit testing, SVG geometry, accessibility, console output, and performance as text;
- the same probe runs inside real VS Code through WebdriverIO;
- fixtures and the real Rust service are both supported;
- readiness is deterministic and requires no arbitrary sleep;
- a human no longer needs to reload the extension merely to tell the agent whether layout moved or broke.
