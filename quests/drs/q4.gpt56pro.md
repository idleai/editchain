## 1. Goal

Build a VS Code explorer for a unified engineering history composed of:

- EditChain operations imported from Claude Code or produced by other writers;
- Git commits imported into EditChain with their full OIDs and ancestry; and
- live Git objects read on demand from the workspace’s actual `.git` repositories.

EditChain remains the reusable history, graph, and retrieval layer. Git commit OIDs provide the stable bridge from imported records to authoritative live commit, tree, blob, and diff data.

The viewer does **not** require every EditChain operation to map to a commit, a lot of record model actions / tool calls will not correspond to a commit, yet the last edit chain that performed explicit git action like git push would. Explicit links are displayed when present; unlinked work and unlinked commits are normal.

EditChain lexical and hybrid search must work across both work history and Git history.

## 2. Core decisions

1. **Read-only viewer.** It does not mutate Git, the worktree, index, branches, commits, or canonical EditChain storage. Disposable indexes and caches are allowed.
2. **Rust-first architecture.** Import, repository resolution, graph projection, indexing, lexical/hybrid search, clustering, and layout live in reusable Rust crates.
3. **Thin TypeScript shell.** TypeScript owns VS Code activation, service lifecycle, webview lifecycle, and message forwarding.
4. **Git is a first-class history source.** Commits can be imported into EditChain and can also be discovered directly from live workspace repositories.
5. **Stable Git identity.** A commit is identified by repository identity, object format, and full OID—not by timestamp, branch name, or abbreviated SHA alone.
6. **Sparse explicit links.** EditChain operations or clusters may link to zero, one, or several Git objects.
7. **No invented provenance.** Similar timestamps, paths, text, or embeddings may affect search ranking but never create graph relationships.
8. **One query layer.** Lexical and hybrid search return heterogeneous EditChain and Git results through the same API.
9. **Live Git is authoritative for object contents.** Imported metadata remains usable when an object is unavailable, but live `.git` data wins when successfully resolved.
10. **Windowed UI projection.** The webview never receives the complete graph or search corpus.

Persisting a Git import is a separate Rust capability such as `editchain import git`; opening the viewer never writes it implicitly.

## 3. Unified history model

The Rust projection contains typed entities and typed relationships:

```rust
pub enum HistoryNodeId {
    EditOperation(OpId),
    GitCommit {
        repository: RepositoryId,
        oid: GitOid,
    },
}

pub enum HistoryEdge {
    Causal {
        parent: OpId,
        child: OpId,
    },
    GitParent {
        repository: RepositoryId,
        parent: GitOid,
        child: GitOid,
    },
    ExplicitGitLink {
        source: OpId,
        target: GitObjectRef,
        relation: GitLinkKind,
    },
}
```

The edge domains remain distinct:

- `Causal` means EditChain dependency.
- `GitParent` means commit ancestry.
- `ExplicitGitLink` means a relationship recorded by an importer or producer.

A Git link never becomes a causal parent merely because both appear in one view.

### Git commit entity

```rust
pub struct GitCommitEntity {
    pub repository: RepositoryId,
    pub object_format: GitObjectFormat,
    pub oid: GitOid,
    pub imported_record: Option<OpId>,
    pub availability: GitAvailability,
    pub tree: GitOid,
    pub parents: Vec<GitOid>,
    pub author: GitSignature,
    pub committer: GitSignature,
    pub authored_at: i64,
    pub committed_at: i64,
    pub message: Payload,
    pub imported_refs: Vec<Payload>,
    pub live_refs: Vec<Payload>,
    pub changed_paths: Vec<PathId>,
}
```

A commit may be:

- **Imported only:** represented in EditChain but absent from the current object database.
- **Live only:** discovered from `.git` and represented in a disposable projection/index.
- **Imported and resolved:** one merged entity keyed by `(RepositoryId, GitOid)`.

Refs are snapshots and may change. Commit, tree, and parent OIDs are immutable identifiers.

### Explicit links

```rust
pub enum GitLinkKind {
    BasedOn,
    Checkpoint,
    CommittedAs,
    ProducedBy,
    Mentions,
    Custom(Payload),
}
```

The viewer displays the stored relation without strengthening or reinterpreting it.

## 4. Git import and live repository resolution

### Git import

The reusable Git importer should preserve at minimum:

- repository identity and object format;
- full commit, tree, and parent OIDs;
- author, committer, timestamps, and message;
- refs observed at import time;
- changed paths and diff statistics;
- optional bounded diff chunks for deeper search;
- explicit EditChain-to-Git links when supplied by the source.

Import must be deterministic and idempotent by `(RepositoryId, GitOid)`.

### Live resolution

The workspace service must:

1. discover repositories and worktrees in the VS Code workspace;
2. match stored repository identity to the correct repository;
3. verify SHA-1/SHA-256 object format;
4. confirm that an OID exists before hydration;
5. read commit, tree, blob, ref, and diff data without mutating or fetching;
6. retain imported data when live resolution fails.

Resolution states:

- `Resolved`
- `ImportedOnly`
- `LiveOnly`
- `MissingFromObjectDatabase`
- `RepositoryMismatch`
- `AmbiguousRepository`

The viewer must never fetch from a remote automatically.

## 5. Graph experience

### Primary EditChain graph

The main graph remains EditChain-centric and uses deterministic topological ordering over causal parents. It supports:

- causal branches, joins, crossings, and missing-parent continuations;
- expandable operation, turn, session, and tool-lifecycle clusters;
- filters by source, kind, actor, session, path, tag, repository, ref, and time;
- lazy inspection of payloads, diffs, commands, and raw records;
- stable selection while external writers append to the chain.

### Git history

Git commits can appear as:

- a dedicated Git rail beside the EditChain graph;
- a separate Git-only graph or pane; or
- commit anchor rows in a unified history projection.

Git ancestry uses visually distinct `GitParent` edges. Cross-domain connectors are drawn only for explicit stored links. The absence of a connector is expected and does not imply missing data.

### Inspector

A Git selection shows imported metadata, live resolution state, current refs, parents, tree, changed files, diff, and explicitly linked EditChain entities.

An EditChain selection shows its normal operation details plus any stored Git references or links.

## 6. Unified lexical and hybrid search

One Rust query API searches a heterogeneous corpus.

### EditChain documents

- user and assistant messages;
- tool names, arguments, and result excerpts;
- commands and output excerpts;
- file paths, edit summaries, and available diff text;
- reflections, notes, errors, actors, sessions, tags, and timestamps.

### Git documents

- full and abbreviated commit OID;
- subject and body;
- author and committer identity;
- imported and live refs;
- changed paths and diff statistics;
- optional chunked patch hunks or selected blob text.

### Retrieval requirements

- Lexical search uses fielded BM25-style retrieval.
- Hybrid search combines lexical and vector results through EditChain rank fusion.
- Vector documents are bounded, source-aware chunks.
- Diff chunks are grouped by commit so a large commit cannot dominate the result set.
- Imported and live versions of the same commit are deduplicated by `(RepositoryId, GitOid)`.
- Results include source kind, stable entity ID, matched fields, snippets, score components, and navigation target.
- Filters include `source:editchain`, `source:git`, repository, author, actor, session, path, ref, operation kind, and date range.
- Selecting a Git result navigates to the commit and hydrates live `.git` details when resolvable.

The default Git profile indexes messages, identities, refs, changed paths, and diff summaries. Full patch-chunk indexing is optional because of storage and privacy cost.

Search similarity discovers related entities but never creates a persisted or visual graph link.

```text

  editchain-codec/             durable encoding
  editchain-node/              chain storage and tail state
  editchain-import/            Claude and Git import adapters
  editchain-git/               repository discovery, object resolution, diffs
  editchain-query/             query model and rank fusion
  editchain-index/             heterogeneous lexical/vector indexes
  editchain-project/           UI-neutral history projections
  editchain-layout/            deterministic typed-edge lane layout
  editchain-protocol/          versioned request/response DTOs
  editchain-vscode-service/    stdio server and orchestration
```

Pure portions of query, projection, and layout should avoid filesystem/process dependencies so they can later target WASM. Git object access and persistent indexing remain native adapters.

Every response carries chain, Git, and index generations so stale windows and results can be detected. Large payloads and diffs are fetched only on demand.

## 10. Performance and security

Target at least 130,000 EditChain operations plus substantial Git history without transferring the full corpus to the webview.

- Cursor-based graph and result windows with overscan.
- Incremental chain and Git indexing keyed by generation and OID.
- Content-addressed deduplication of commit and diff chunks.
- Lazy live Git hydration and bounded caches.
- No per-row cloning of complete lane state.
- Restrictive webview CSP and sanitized Markdown, JSON, terminal output, commit text, and diffs.
- Stdio instead of an unauthenticated local port.
- No command replay, Git mutation actions, or remote fetch.
- No raw histories, repository contents, or diffs in telemetry.

## 11. Delivery sequence

### Phase 1 — Git-aware EditChain model

- Add typed Git commit and explicit-link records.
- Add repository identity and SHA-1/SHA-256-safe object IDs.
- Implement deterministic causal and Git ancestry projections.
- Add idempotent `editchain import git`.

### Phase 2 — Unified Rust retrieval

- Extend lexical and hybrid indexes to imported and live Git documents.
- Add source-aware chunking, deduplication, grouping, filters, and snippets.
- Expose mixed EditChain/Git search through CLI and reusable APIs.

### Phase 3 — Live Git resolver

- Discover workspace repositories and worktrees.
- Merge imported and live commit entities by repository/OID.
- Hydrate commits, trees, blobs, refs, and diffs.
- Handle missing, shallow, ambiguous, and mismatched repositories without fetching.

### Phase 4 — VS Code explorer

- Add the thin TypeScript extension and Rust stdio service.
- Render virtualized EditChain history plus Git rail/pane.
- Render only explicit cross-domain links.
- Add unified lexical/hybrid search and live Git inspection.

### Phase 5 — Broader EditChain surfaces

- Reuse the model, retrieval, projection, and protocol in the TUI and CLI.
- Add a persistent daemon/API when multiple clients need shared indexes.
- Compile pure query/projection/layout crates to WASM where useful.

## 12. Acceptance criteria

- Git commits import with repository identity, full OIDs, trees, and parent ancestry preserved.
- Imported and live versions of the same commit merge into one history entity.
- Preserved OIDs resolve to the correct workspace `.git` repository when objects exist.
- Missing or shallow objects do not invalidate imported history.
- The viewer remains read-only and never mutates Git or canonical EditChain storage.
- EditChain causal edges, Git ancestry edges, and explicit links remain visibly and semantically distinct.
- Unlinked operations and commits render normally.
- No timestamp, path, branch, or semantic similarity automatically becomes a graph relationship.
- One lexical/hybrid API returns both EditChain and Git results.
- Git search covers at minimum commit message, identity, refs, changed paths, and diff summary; bounded patch chunks are optional.
- Selecting a Git result navigates to the commit and opens live details when resolvable.
- A large chain and Git repository open without transferring the complete graph or index to the webview.
- TypeScript contains minimal product logic; the Rust layer is reusable by CLI, TUI, daemon, and future surfaces.
- No implementation code or assets are copied from the reference viewer.
